# 学習ドキュメントの作成

`docs/` は**作業日誌ではなく、後から見返して思い出すためのリファレンス**として書く。
参画後に「あれどうだっけ」と開いたとき、そのファイルだけで思い出せることがゴール。

## 流れ

1. このセッションで学んだことを振り返り、**トピック単位**に整理する
2. ファイル名は **`NN-テーマ.md`**（日付は付けない）。`NN` は `docs/` 内の既存ファイルの続きの連番
   - 例: `01-vue3-project-setup.md`、`02-vue3-ref-reactive.md`
   - 既存ファイルと同じテーマなら、新しく作らずにそのファイルへ追記する
3. 下の構成で書く
4. 書いたら、**空で渡した欄がどこか**を明示して伝える

## 構成

```markdown
# テーマ名

Phase N / ステップN（YYYY-MM-DD）

このドキュメントで何がわかるかを1〜2行で。

---

## 1. トピック
## 2. トピック
...

---

## 自分の言葉で

### 口頭で説明するなら

<!-- 自分の言葉で埋める -->

### 一度やったはずなのに忘れていたこと

<!-- 自分の言葉で埋める -->
```

### 各トピックに入れるもの

- **コード例**：要点だけ。ファイル全文は貼らない（リポジトリに実物がある）
- **既に知っている技術との対比表**：React / Next.js / Vuex / Express / TypeScript など
- **なぜこの書き方なのか**：選択の理由、トレードオフ
- **ハマりどころ・注意点**：間違えやすい点、実務で見かけるもの
- 学習中に理解を補正したこと（例：「1回だけ実行」→ 正確には「インスタンスごとに1回」）は、**正しい内容として本文に反映**する。誤解していた経緯を別の欄に書く必要はない

## 本人が書く欄

| 欄 | 扱い |
|---|---|
| トピックごとの本文 | 代筆してよい。見返して思い出せることを優先して書く |
| **口頭で説明するなら** | **空で渡す** |
| **一度やったはずなのに忘れていたこと** | **空で渡す** |

この2つは本人が書かないと意味がない。代筆すると、読み返したときに自分の理解の記録にならない。
**空欄のまま渡し、「ここは自分の言葉で埋めてください」と伝える。**

## 守ること

- **事実だけ書く。** やっていないことを書かない。試していないコードを「確認した」と書かない
- **1テーマ1ファイル。** 長くなりすぎたらテーマを分ける
- 案件の固有名詞（企業名・システム名・社内独自ライブラリ名）を書かない。公開リポジトリになる可能性がある

## 書いたあと

- `git add docs/ && git commit` を促す。**ドキュメントのコミットが学習ログになる**
- `explain-check` で「曖昧」と出た項目があれば、それを本文に反映する
