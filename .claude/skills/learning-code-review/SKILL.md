# 学習者向けコードレビュー（TypeScript / Vue / NestJS）

目的はコードを直すことではなく、**コードの良し悪しを自分で判断できるようになること**。
レビュー内容を写して直せてしまうと、判断力は身につかない。

対象は `.ts` / `.vue` / NestJS のコード。**Javaのコードはこのスキルでは扱わない。**

## 絶対に守ること

- **修正後のコードを書かない。** 差分もパッチも出さない
- 「どう直すか」は本人に考えさせる
- **指摘は5つまで。** それ以上並べると手が止まる
- 指摘には必ず理由をつける。「慣習だから」で終わらせない
- 本人が直すまで、次のトピックに進まない

## 流れ

1. **対象を確認する。** ファイル指定がなければ `git diff` か直近の変更を対象にする
2. 読んで、指摘を重要度順に並べる
3. 各指摘は下のフォーマットで書く
4. 最後に**良かった点を1つ以上**挙げる。何が正しいのかも判断材料になる
5. 本人が直して「再レビュー」と言われたら2周目。**前回の指摘が解消したかを先に確認**してから新しい指摘に入る

## 指摘のフォーマット

```
### [必須|推奨|好み] 見出し

**場所**: ファイル名:行番号
**何が問題か**: 1〜2行
**なぜ問題か**: このまま進めると何が起きるか
**考えるヒント**: 答えではなく、調べる方向だけ
```

重要度の使い分け：

| 重要度 | 基準 |
|---|---|
| 必須 | バグ、型の穴、責務の混在。直さないと後で必ず困る |
| 推奨 | 動くが読みにくい、テストしにくい |
| 好み | 書き方の選択。**必須に混ぜない** |

## 観点

**TypeScript**
- `any` と `as` を使っていないか。使うなら理由があるか
- 型を再定義していないか（`Pick` / `Omit` / `Partial` で派生できないか）
- 共通で使う型が1箇所にまとまっているか
- 関数の戻り値の型が推論に頼りすぎていないか

**Vue 3**
- `ref` と `reactive` の選択に一貫性があるか
- `computed` で済む処理を `watch` でやっていないか
- `props` / `emit` に型がついているか
- コンポーネントが画面の都合と業務ロジックを混ぜていないか
- 副作用のクリーンアップ（`onUnmounted`）が必要な箇所で漏れていないか

**NestJS**
- Controller が薄いか。**業務ロジックが Controller に漏れていないか**
- Service が1つのことをしているか
- DTO で入力検証をしているか。Controller の中で手書きしていないか
- BFFとして、複数のデータ取得をまとめる責務に留まっているか（業務ロジックを持っていないか）

**共通**
- 命名が「何をするか」を表しているか
- 関数が1つのことをしているか
- テストを書けるか（書けないなら設計に原因がある）
- エラー時に何が起きるか説明できるか

## やらないこと

- 全部を指摘する。優先順位のない指摘は無視されて終わる
- 好みの問題を必須として出す
- 修正コードを「参考として」出す。**参考として出したものは写される**
- 誉めるだけで終わる。良かった点は1つで足りる
